# STIX 2.1 export

The tracker's curated intelligence is published as one STIX 2.1 Bundle, so you
can load it into a CTI platform instead of transforming the JSON feeds yourself.

**Download:**
[`data/india-threat-tracker-stix.json`](data/india-threat-tracker-stix.json)
(raw: `https://raw.githubusercontent.com/sohankanna/india-threat-tracker/main/data/india-threat-tracker-stix.json`)

It is generated by [`scripts/build_stix.py`](scripts/build_stix.py) from the
canonical feeds, rebuilt by every automated update, and checked in CI. Data is
CC BY 4.0; credit Sohan Kanna / India Threat Tracker.

## What is in it

| STIX object | From | Notes |
|---|---|---|
| `identity` (1) | — | "India Threat Tracker", the `created_by_ref` of every object |
| `campaign` | `smishing-apk.json` records | Reference records (category "Reference: …") are not campaigns and are not exported |
| `intrusion-set` | `apt-campaigns.json` records | Never `threat-actor`; reported attribution stays in the description (see below) |
| `indicator` | campaign `iocs.domains`, `iocs.urls`, `iocs.sha256` | Only types with an unambiguous standard pattern |
| `malware` | named families: campaign records naming one, actor `known_tools` | Generic capability names (e.g. "Backdoor loaders") are excluded; `is_family: true` |
| `attack-pattern` | ATT&CK techniques on campaigns and actors | `external_references` carries the technique id (`source_name: mitre-attack`) |
| `vulnerability` | CVEs the monthly assessment cites as evidence | Not all ~1,750 KEV entries: only those the analysis relies on |
| `report` | `assessment.json` | Marked as analyst judgement; `object_refs` lists the cited records |
| `relationship` | explicit links in the data | See below |
| `marking-definition` | — | TLP:WHITE: the data is public and CC BY 4.0 |

Relationships, and only these:

| Source | Type | Target | Basis |
|---|---|---|---|
| indicator | `indicates` | campaign | The indicator is listed on that campaign by its source |
| campaign | `uses` | attack-pattern | Techniques the tracker mapped from the reported behaviour |
| campaign | `uses` | malware | The campaign record names the malware family |
| intrusion-set | `uses` | attack-pattern | As above, for actors |
| intrusion-set | `uses` | malware | The actor's tools as named in vendor and MITRE reporting |

No `attributed-to` relationships are asserted. Campaign and actor records are
kept separate because the sources do not link them.

## Provenance and uncertainty

* **Sources:** every campaign, intrusion set and indicator carries its source
  reports as `external_references` (title and URL), plus a reference back to the
  tracker record (`source_name: india-threat-tracker`, `external_id` = tracker
  id). The sources do not give publication dates in the tracker data, so none
  are invented.
* **Confidence:** the tracker's own high / medium / low rating of the evidence,
  mapped with the STIX 2.1 Appendix A "High, Medium, Low" scale: 85 / 50 / 15.
  Indicators inherit the confidence of the campaign that reports them. On actors
  it rates the evidence for the activity, not the attribution.
* **Attribution:** stated in the intrusion set's description as "Reported
  attribution: …" with the basis, and on campaigns as "Attribution as reported:
  …", including "allegations, not yet proven in court" for police actions.
* **Timestamps:**
  * `created`: the date the tracker first published the record (`date_added`),
    or the assessment date for the report and the CVEs it cites.
  * `modified`: carried forward unchanged while an object's content is
    unchanged; moved forward when it changes.
  * `valid_from` on indicators: the date the tracker began publishing the
    indicator. **It is not an observation date.**
  * `first_seen` / `last_seen` are not set. Where a source gives only a month
    ("2025-09"), it appears in the description as "First reported: 2025-09"
    instead of being turned into a false-precision timestamp.
  * `published` on the report: the assessment date.
* **Reported fact versus analysis:** campaign and actor descriptions carry
  source-reported findings. The report is labelled as analyst judgement.

## Indicators, and what is deliberately not one

* Patterns use real values (`[domain-name:value = 'jsonserv.xyz']`), not the
  defanged forms shown on the website. Every value is checked against its type
  (hostname syntax, 64-hex SHA-256, http(s) URL) and quoted per the STIX
  pattern grammar before it goes into a pattern, so a malformed value cannot
  change a pattern's logic. Every pattern is also checked with the OASIS
  pattern validator.
* **Infrastructure context is never an indicator.** GitHub, Firebase, hosting
  providers and C2 technologies a campaign abused are listed in the campaign
  description under "Infrastructure context, not indicators … do not block".
* Android package names and Telegram bot handles have no well-fitting standard
  STIX pattern; they are listed in the campaign description instead of being
  forced into one.
* Indicators are **as reported, not re-validated**. Alert on them before you
  block them, and expect some to be stale.

## Stable identifiers

Every object id is a random UUIDv4, as STIX 2.1 recommends, generated **once**
per tracker key (campaign id, technique id, relationship triple) and committed
in [`stix/id-registry.json`](stix/id-registry.json). Later builds reuse it, so an
object keeps its id for life and platforms update it in place rather than
creating duplicates. Rebuilding unchanged data produces a byte-identical file.
The bundle id stays the same while the content does and changes when it changes.

## Validation

CI runs on every push and pull request:

* `python scripts/build_stix.py --check`: the committed bundle is exactly what
  the current feeds produce, and every object has a committed id.
* `stix2_validator data/india-threat-tracker-stix.json`: the OASIS validator,
  against the official STIX 2.1 JSON schemas.
* `tests/test_stix.py`:
  * the bundle is current;
  * it is schema-valid;
  * every pattern is valid;
  * referential integrity holds, with no duplicate ids;
  * every indicator traces to a campaign IOC, and no infrastructure appears in any pattern;
  * stability: rebuilds are identical, a changed record keeps its id and `created` and gets a later `modified`;
  * one test per mapping rule, including records with optional fields missing;
  * malformed IOC values are rejected rather than injected.

To run it yourself:

```bash
pip install -r requirements.txt
python scripts/build_stix.py --check
stix2_validator data/india-threat-tracker-stix.json
python -m unittest tests.test_stix -v
```

**Known validator warning:** in `--strict` mode the validator reports
`{302} External reference … has a URL but no hash` for every web reference.
Hashing a news article or blog post is not meaningful (pages change), so this
recommendation is not followed. It is the only accepted deviation; the test
suite fails on any other strict-mode finding.

`stix2-validator` is pinned to 3.2.0 because the 3.3.x wheels ship without the
OASIS JSON schemas and cannot validate anything.

## Importing into a CTI platform

### MISP: tested with the import library; instance import pending

The bundle has been converted with **misp-stix 2026.10.12**, the library MISP
itself uses to import STIX 2.1 (MISP's `/events/upload_stix/2` calls it). This
runs in CI on every change (`tests/test_interop_misp.py`). Result:

| In the bundle | In MISP |
|---|---|
| Report (monthly assessment) | 1 event, with the assessment text as an event report |
| 5 indicators | 5 attributes (3 `sha256`, 2 `domain`), all `to_ids`, each with the source note and a confidence tag, each linked to its campaign |
| 6 campaigns | campaign galaxy clusters (4 on the event, the 2 with only indicator links on their attributes) |
| 4 intrusion sets, 13 malware, 25 techniques, 6 CVEs | galaxy clusters with descriptions, created/modified dates and references |
| TLP:WHITE marking, producer identity | `tlp:white` and producer tags |
| Infrastructure context | not an attribute (stays in descriptions) |

**Lost in MISP, by design of the mapping:**
* The 54 `uses` relationships (campaign or intrusion set → technique or
  malware). MISP attaches every cluster to the event with no cluster relations,
  so you can no longer see which technique belongs to which actor.
* Intrusion-set aliases (APT36, Mythic Leopard…) survive only inside the
  description, not as MISP synonyms.

**Instance import:** [`.github/workflows/interop-misp.yml`](.github/workflows/interop-misp.yml)
starts a disposable MISP 2.5.50 from the official
[misp-docker](https://github.com/MISP/misp-docker) images, uploads the bundle
through MISP's own STIX import and reads back what was stored
([`interop/misp_import.py`](interop/misp_import.py)). Its recorded result goes
here once it has run; until then, treat the instance import as **not yet
confirmed**.

### OpenCTI

**Untested.** Upload the bundle through the data import screen (STIX file import

## Sample

The GhostBat campaign, abbreviated:

```
campaign  "GhostBat RAT - RTO/mParivahan-themed Android campaign"  confidence 85
  ├─ uses ─▶ malware "GhostBat RAT"
  ├─ uses ─▶ attack-pattern T1660 Phishing, T1417.002 GUI Input Capture, …
  └─ description: "… Also reported, not expressed as STIX patterns: Telegram bot
     GhostBatRat_bot. Infrastructure context, not indicators (… do not block):
     raw.githubusercontent.com; github.com (releases); Firebase Cloud Messaging …"

indicator "[domain-name:value = 'jsonserv.xyz']" ─ indicates ─▶ campaign "RTO Challan fraud …"
report "India threat assessment, October 2026" ─ object_refs ─▶ campaigns, intrusion sets, CVEs
```

## Limitations

* Small by design: only what the tracker curates and can source.
* No source publication dates, so none are exported.
* Detection rules are not exported as STIX `indicator`s with
  `pattern_type: sigma`; they are linked from the report instead.
* OpenCTI import is untested; MISP is tested at library level, instance import pending (see above).
